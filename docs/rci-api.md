# The Keenetic RCI API

Notes taken while building [keenetic-mcp](https://github.com/salatmaster/keenetic-mcp).
Keenetic does not publish coherent documentation for RCI, so everything here was
established against a live **Keenetic Ultra (KN-1811) running KeeneticOS 5.1.3**
and is marked where it was not.

RCI is a standard part of KeeneticOS rather than a feature of high-end models,
and has existed since the NDMS 2.x era. What differs between routers is the set
of available paths, which follows the installed components.

## What it is

RCI is not REST. It is a **JSON mirror of the command-line tree**: a URL path is
a path through the same tree you would walk in the CLI.

| Request | Meaning |
|---|---|
| `GET /rci/show/...` | operational state, the equivalent of a `show` command |
| `GET /rci/<config path>` | the running configuration as JSON |
| `GET /rci/` | the entire running configuration, about 35 KB |
| `POST /rci/` | a command object, or an array of them for batching |

The top level of the configuration tree:

```
system  schedule  known  isolate-private  user  interface  ip  object-group
ipv6  ppe  upnp  service  cifs  dns-proxy  mdns  mws  easyconfig  components  cloud
```

There is **no introspection**. `GET /rci/show` returns `[]`; the tree does not
describe itself.

## Authentication

Neither HTTP Basic nor Digest works on the LAN web port; both return 401. Digest
is only accepted through the HTTP Proxy service on port 79, which is disabled by
default.

The LAN scheme is challenge-response:

```
GET /auth
  -> 401
     WWW-Authenticate: x-ndw2-interactive realm="Keenetic Ultra"
                       challenge="<32 chars>" session_cookie="<random name>"
     X-NDM-Realm:     Keenetic Ultra
     X-NDM-Challenge: <32 chars>
     Set-Cookie: <random name>=<sid>; Max-Age=300; HttpOnly; SameSite=Strict

md5 = MD5(login + ":" + realm + ":" + password)    // lowercase hex
key = SHA256(challenge + md5)                       // lowercase hex

POST /auth  {"login": "<login>", "password": "<key>"}
  -> 200, session established in the cookie
```

In Node:

```js
import { createHash } from 'node:crypto';

const md5 = createHash('md5').update(`${login}:${realm}:${password}`).digest('hex');
const key = createHash('sha256').update(`${challenge}${md5}`).digest('hex');
```

### Four things that break naive clients

**The cookie name is randomised.** It is generated by the router, so it must be
read from `Set-Cookie` or from the `session_cookie=` field of the
`WWW-Authenticate` header. A cookie jar handles this for free; a hand-written
header does not.

**The session is a 300-second sliding window.** Every request extends it.
Measured directly: the cookie expiry advanced after a single call. Five idle
minutes log you out, which is an ordinary gap between questions in an agent
conversation, so a client must re-authenticate transparently on 401 rather than
authenticating once at startup.

**The realm varies by model.** It is `"Keenetic Ultra"` on this hardware and
will differ on yours, so it has to come from the response rather than a
constant.

**Over KeenDNS the `X-NDM-*` headers are absent.** Defaulting them to empty
strings produces a hash of empty input and an opaque 401. Remote access uses a
different scheme, not covered here.

Requests originating from `127.0.0.1`, which means from inside the router under
Entware, need no credentials at all.

The router tolerates repeated session creation: fifteen consecutive
authentications all succeeded and an existing session survived them.

## Errors

**The router frequently answers HTTP 200 with the failure inside the body:**

```json
{"status":[{"status":"error","code":"6553609",
  "ident":"Network::Interface::Base","message":"unable to find (empty)."}]}
```

A nonexistent path returns 404 with an empty body. A client must therefore check
both the HTTP status and walk the body for `status[].status == "error"`.

**Not every status block is a failure.** A successful write returns the same
shape at a different level:

```json
{"status":[{"status":"message","message":"rule \"permit\" applied to host \"...\"."}]}
```

Treat only `error` as fatal.

Error messages embed the requesting client's IP, as in
`no input [http/rci <your address>]`.

## Response sizes

The constraint when feeding this to a language model is the context window, not
the router: latency is 13 ms for `show/system` and about 100 ms for 100 KB.

| Path | Size | Format |
|---|---|---|
| `show/ip/nat` | over 100 KB, hundreds of rows | JSON |
| `show/processes` | about 70 KB | JSON |
| `show/netfilter` | about 34 KB | **plain text, not JSON** |
| `/rci/` | about 35 KB | JSON |
| `show/interface` | about 32 KB | JSON |
| `show/running-config` | about 15 KB | **array of CLI lines** |
| `show/ip/hotspot` | about 10 KB for nine devices | JSON |

## Capability detection

`GET /rci/show/version` reports what the router actually has:

```json
{
  "title": "5.1.3",
  "model": "Ultra (KN-1811)",
  "hw_id": "KN-1811",
  "ndw": {
    "components": "base,cloudcontrol,dhcpd,dns-tls,ip6,wireguard,...",
    "features": "wifi5ghz,wifi6_5ghz,hwnat,wpa3,link_agg,..."
  }
}
```

`components` is what is installed, `features` is what the hardware supports.
This is the reliable way to decide whether a feature exists before trying to use
it.

## Recovering the syntax of a command

**The most useful technique here.** The router stores its own configuration as
valid CLI, so it will show you the exact syntax of anything it is already doing:

```
GET /ci/running-config.txt
```

For example, the device access section appears as:

```
ip hotspot
    host <mac> permit
    host <mac> policy Policy0
```

which maps directly to:

```json
{"ip":{"hotspot":{"host":{"mac":"<mac>","policy":"Policy0"}}}}
```

Guessing field names instead produces silent no-ops, described below.

## Writing

### Device settings live in two branches

Naming and registration are under `known`. Access, policy, schedule and priority
are under `ip/hotspot`. All confirmed against a live router:

| Setting | Command |
|---|---|
| name, and registration | `{"known":{"host":{"mac":"…","name":"…"}}}` |
| allow | `{"ip":{"hotspot":{"host":{"mac":"…","permit":true}}}}` |
| block | `{"ip":{"hotspot":{"host":{"mac":"…","deny":true}}}}` |
| routing policy | `{"ip":{"hotspot":{"host":{"mac":"…","policy":"Policy0"}}}}` |
| schedule | `{"ip":{"hotspot":{"host":{"mac":"…","schedule":"schedule0"}}}}` |
| priority | `{"ip":{"hotspot":{"host":{"mac":"…","priority":5}}}}` |
| remove entirely | `{"known":{"host":{"mac":"…","no":true}}}` |

A host must exist in `known` before `ip/hotspot` accepts any setting for it;
otherwise the router answers `host "…" is unregistered`. Setting a name
registers it.

**Removal only works through `known`.** `{"no":true}` against `ip/hotspot/host`
is refused with `"no" is not applicable to: host`. Removing the `known` entry
cascades and drops the access settings with it.

### Interfaces

```json
{"interface":{"Bridge0":{"up":true}}}          // bring up
{"interface":{"Bridge0":{"up":{"no":true}}}}   // bring down
```

`{"no": true}` nested inside a field is the general negation form.

### Saving

```json
{"system":{"configuration":{"save":{}}}}
```

The reply is `{"status":[{"status":"message","message":"saving (http/rci)."}]}`,
in the present tense, so the write may still be in flight. Poll
`show/last-change` rather than checking once.

## Three traps

**A wrong field name is a silent no-op.** Sending `name` into the `ip/hotspot`
branch, where it does not exist, returns `{}` with no error and changes nothing.
That is more dangerous than a rejection, because it looks exactly like success.
Read every write back and compare it against what you intended.

**A config branch does not echo what you write to it.** `GET /rci/known/host`
returns `[{"mac":"…"}]` and never includes the name, even directly after a
successful rename. Verify against whichever view actually exposes the field,
which for names is `show/ip/hotspot`.

**Interface names containing a slash cannot be fetched by path.** Every Wi-Fi
access point is named like `WifiMaster0/AccessPoint0`, and the slash is read as
another path segment, so `GET /rci/show/interface/WifiMaster0/AccessPoint0` is a
404. URL-encoding the slash does not help. Ask by name instead:

```json
{"show":{"interface":{"name":"WifiMaster0/AccessPoint0"}}}
```

## Configuration persistence

**Writes apply to the running configuration and are not persisted.** A reboot
discards them unless `system configuration save` runs.

`GET /rci/show/last-change` reports the state:

```json
{"date":"…","agent":"http/rci","user":"admin","checksum":"…",
 "fail-safe":{"action":"","unsaved":false,"time-left":0,
              "rollback":false,"blocked":false}}
```

The built-in **fail-safe is a connectivity watchdog, not a commit-confirm**. A
three-minute timer starts when changes are applied, and the router reverts to
the startup configuration only if the management session **loses connectivity**.
It protects against locking yourself out. It does not protect against a change
that is wrong but still leaves the router reachable.

## Configuration files

| Path | Contents |
|---|---|
| `GET /ci/startup-config.txt` | the saved configuration, as CLI text |
| `GET /ci/running-config.txt` | the live configuration, as CLI text |

Both return `application/octet-stream`, about 12 KB on a home router. `POST` to
these paths returns 405, so there is no upload path here; restoring a
configuration through RCI was not solved.

## Paths that do not exist

Do not assume an installed component implies a path of the same name. All 404 on
5.1.3, `wireguard` component installed and WireGuard interfaces live:

`show/wireguard`, `show/log`, `show/ipsec`, `show/components/list`,
`show/ntce`, `show/skydns`, `show/wlan`

WireGuard state is under `show/interface/Wireguard3`.

## A useful path index

| Path | Contents |
|---|---|
| `show/version` | model, firmware, components, hardware features |
| `show/system` | hostname, CPU load, memory, uptime, conntrack |
| `show/interface` | every interface |
| `show/interface/<name>` | one interface, no slash in the name |
| `show/ip/hotspot` | every known device with full telemetry |
| `show/ip/dhcp/bindings` | DHCP leases |
| `show/ip/route` | routing table |
| `show/ip/nat` | live NAT table, very large |
| `show/associations` | Wi-Fi stations |
| `show/internet/status` | reachability checks |
| `show/last-change` | last change, and whether it is saved |
| `show/ndns` | KeenDNS registration |
| `show/dns-proxy` | DNS proxy state |
| `show/media` | attached storage |
| `show/schedule` | defined schedules |
| `show/processes` | process list, large |
| `show/netfilter` | firewall rules, plain text |
| `ip/hotspot/host` | per-device access configuration |
| `known/host` | device registration |
| `ip/policy` | connection policies |
| `ip/static` | port forwarding |
| `interface/<name>` | one interface's configuration |
| `system` | system configuration |
| `user` | accounts |
| `components` | component settings |
